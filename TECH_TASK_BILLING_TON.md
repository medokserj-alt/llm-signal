# Техническое задание: Billing‑сервис для подписок в TON

## 1. Цель
Разработать отдельный billing‑сервис, который:
- принимает оплату подписки в TON за периоды 1/3/6/9/12 месяцев;
- ведёт учёт подписок пользователей Telegram;
- интегрируется с существующими ботами (`tg_bot.py`, `tg_signal_bot.py`) для управления доступом.

**Доступ по оплате:** оплата предоставляет доступ к `@LLM_signals_pa_dev_bot` (signal‑бот).

## 2. Область работ
Входит:
- проектирование и реализация billing‑сервиса (HTTP API + БД);
- интеграция с TON (отслеживание платежей);
- интеграция с ботами (активация/истечение подписки);
- логирование, мониторинг, алерты.

Не входит:
- UI/фронтенд (если не оговорено отдельно);
- миграция исторических оплат (можно отдельной задачей).

## 3. Термины
- **Core‑бот**: `tg_bot.py`, получает команды и генерирует сигналы.
- **Signal‑бот**: `tg_signal_bot.py`, витрина оплаты/статуса.
- **Подписка**: право на получение сигналов в течение оплаченного периода.

## 4. Функциональные требования
### 4.1 Тарифы
- Поддержка периодов: 1, 3, 6, 9, 12 месяцев.
- Цена в TON задаётся конфигом.

### 4.1.1 Управление ценами
- Цены хранятся в конфиг‑файле на хосте (например `billing_prices.json` или `.env`).
- Администрирование цен: правка конфиг‑файла + перезапуск сервиса.
- Валидация: для каждого периода должна быть задана положительная цена в TON.

### 4.2 Выставление счёта
- Создание invoice с:
  - адресом для оплаты;
  - уникальным комментарием/мемо;
  - суммой в TON;
  - сроком жизни (TTL).
- Возврат клиенту деталей платежа.
 - Цена фиксируется на момент создания invoice и не пересчитывается.

### 4.3 Отслеживание оплаты
- Billing‑сервис отслеживает входящие транзакции на адрес(а) через TON API.
- Оплата считается подтверждённой после N подтверждений (N=1..3, настраивается).
- Сопоставление платежа с invoice по memo и сумме.
- Частичная/избыточная оплата не допускается и не засчитывается (только точное совпадение суммы).

### 4.4 Активация подписки
- При подтверждении оплаты:
  - срок действия = оплаченный период (1/3/6/9/12 месяцев);
  - если подписка активна → продление на оплаченный период;
  - если неактивна → новая подписка до now + оплаченный период.
- Сервис отправляет событие в core‑бот (активация).
 - Оплата привязывается к одному Telegram ID (мульти‑аккаунты не поддерживаются).

### 4.5 Истечение подписки
- Периодическая проверка (`cron/worker`): истёкшие подписки помечаются как expired.
- Сервис отправляет событие в core‑бот (деактивация).

### 4.6 Возвраты
- Возвраты не поддерживаются.

### 4.7 История и статусы
- Статусы invoice: pending, paid, expired, canceled.
- Статусы подписки: active, expired, canceled.

## 5. Нефункциональные требования
- Надёжность: не терять оплату при сбое (идемпотентность).
- Аудит: хранить tx_hash и raw‑payload.
- Безопасность: секреты в env, подпись входящих вебхуков (если есть).
- Масштабируемость: базовая горизонтальная масштабируемость API.

## 6. Архитектура (высокий уровень)
- Billing‑API (REST) + Worker (webhook TON Connect).
- База данных: **SQLite**.
- Интеграция с Telegram‑ботами через HTTP endpoint в core‑боте или через файл/DB.

## 7. Модель данных (рекомендовано)
### users
- telegram_id (PK)
- username
- created_at

### subscriptions
- telegram_id (FK)
- status (active/expired/canceled)
- plan_months (1/3/6/9/12)
- paid_until (UTC)
- last_payment_id

### invoices
- invoice_id (PK)
- telegram_id
- plan_months
- amount_ton
- address
- memo
- status (pending/paid/expired)
- created_at
- paid_at

### payments
- tx_hash (PK)
- invoice_id
- amount_ton
- confirmed_at
- raw_payload (JSON)

## 8. API Billing‑сервиса (пример)
### 8.1 Создать invoice
`POST /v1/invoices`
```json
{
  "telegram_id": 82052103,
  "plan_months": 6
}
```
Ответ:
```json
{
  "invoice_id": "inv_...",
  "address": "EQ...",
  "memo": "uid82052103_inv_...",
  "amount_ton": "12.5",
  "expires_at": "2026-02-15T12:00:00Z"
}
```

### 8.2 Проверка статуса invoice
`GET /v1/invoices/{invoice_id}`

### 8.3 Получить статус подписки
`GET /v1/subscriptions/{telegram_id}`

## 9. Интеграция с ботами
### 9.1 События в core‑бот
Billing‑сервис вызывает endpoint (или пишет в очередь):
- `POST /billing/subscription/activate`
- `POST /billing/subscription/expire`

Payload:
```json
{
  "telegram_id": 82052103,
  "paid_until": "2026-08-15T00:00:00Z",
  "plan_months": 6,
  "invoice_id": "inv_..."
}
```

### 9.2 Изменения в core‑боте
- Добавить поле `paid_until` в `user_registry.json`.
- Проверять `paid_until` в `is_active()`.
- Allow‑лист платных (`TELEGRAM_PA_ALLOWED_USER_IDS`) формируется автоматически при оплате.
- Платный пользователь всегда имеет доступ к меню core‑бота.

## 10. TON‑интеграция (выбранный подход)
**Простой вариант**: TON Connect + TonAPI webhook.
- формирование платежной сессии через TON Connect;
- получение webhook о платеже через TonAPI (обязательно);
- подтверждение платежа после 10 подтверждений;
- TTL инвойса: 60 минут;
- проверка статуса платежа по invoice_id/tx_hash.

## 11. Идемпотентность
- Повторный callback не должен продлевать подписку дважды.
- Уникальность по `tx_hash` и `invoice_id`.

## 12. Мониторинг и алерты
- Ошибки TON API (5xx, таймауты).
- Отсутствие подтверждений за TTL.
- Метрики: число созданных invoice, оплаченных, активных подписок.

## 13. Тестирование
- Unit‑тесты: расчёт `paid_until`, идемпотентность.
- Интеграционные тесты: мок TON API.
- E2E: симуляция оплаты.

## 14. Развёртывание
- Сервис + воркер на **том же хосте**, что и боты.
- Запуск через systemd (предпочтительно) или Docker.
- Секреты в `.env`/Vault.
- Миграции БД через Alembic/SQLx.
